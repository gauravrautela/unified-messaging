How it works

Three calls end to end. Your users never see an API key, and you never store one of their passwords.

1

Mint a hosted-auth link from your server and hand it to your user. They sign in with Microsoft, or scan a QR code for WhatsApp, on our page — you get an account_id back on your notify_url.

Built for developers

The parts you would otherwise build twice.

Webhooks that keep trying

Deliver to your own HTTPS endpoint, a Discord channel, or a Telegram chat. Failures retry with backoff, and every attempt is on the record at GET /api/v1/webhooks/{id}/deliveries.

Idempotency keys

Send with an Idempotency-Key and a repeat of the same key and body replays the original response. Timeouts and retries stop being a duplicate-message problem.

Hosted auth

One POST returns a link. Your user signs in, or scans a QR code, on a page we host and keep working — no OAuth client, no consent screen, no QR plumbing in your app.

llms.txt

The whole API in one plain-text file at /llms.txt, written to be pasted into a coding agent. Your assistant reads the docs so you can skip them.

Self-hostable

One Go binary, SQLite by default or Postgres when you want it. No queue, no broker, no sidecar — run it next to your app and keep the mailbox tokens in your own database.

API keys with rotation

Mint keys from the dashboard, hashed at rest and shown once. Rotation issues the replacement before the old key stops working, so a key can be retired with no downtime.
