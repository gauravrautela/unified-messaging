Entropix API reference

One REST API for your end users’ mailboxes and WhatsApp numbers: connect them with hosted auth, receive every message on your webhook, send with one call. Base URL for this deployment: {{.Base}}.

Quickstart

Five steps from nothing to a message sent as one of your users.

  1. Create an API key. Keys are minted from the dashboard only, so a leaked key cannot mint more keys. Sign in at /login, then Dashboard → New key. The full key is shown exactly once and never stored. {{template "snippet" (index .Snippets "key")}}
  2. Check it is live. GET /api/v1/me is the cheapest call there is: it answers with the developer the credential belongs to and how you authenticated. 
    curl "{{.Base}}/api/v1/me" -H "Authorization: Bearer $API_KEY"
  3. Connect an end user. Mint a single-use link from your server and send the user to it. Your API key never leaves your server and the user never sees your provider credentials. {{template "snippet" (index .Snippets "hosted")}}
  4. Receive their messages. Register a webhook (at connect time, or with POST /api/v1/webhooks) and we POST every event to it, signed and retried. {{template "snippet" (index .Snippets "hook")}}
  5. Send. One endpoint per surface: POST /api/v1/chats/{chat_id}/messages for chat, POST /api/v1/emails for mail. {{template "snippet" (index .Snippets "send")}}

Authentication

Every /api/v1 call carries an API key:

Authorization: Bearer $API_KEY
X-API-Key: $API_KEY          # equivalent, for clients that cannot set Authorization

Keys start with um_. Only a 12-character prefix is stored, so a key you have lost cannot be recovered — revoke it and create another. A revoked or unknown key is 401 unauthorized.

Some endpoints refuse a key on purpose. Creating and revoking keys, changing your password and replacing your redirect-domain allowlist accept a signed-in dashboard session only, and answer 403 session_required to a bearer token. That is the blast radius of a leaked key: it can read and send on the accounts you already connected, but it cannot mint credentials or widen where your users can be redirected.

Tenancy is strict. An account, webhook, message or chat belonging to another developer answers 404, never 403 — ids are not enumerable across tenants.

Mail and chat routes are scoped to exactly one connected account: pass ?account_id=acc_…, or account_id in the body where the endpoint documents it. Without one the answer is 400 missing_account_id.

Hosted auth

You never handle an end user’s provider credentials. POST /api/v1/hosted-auth mints a single-use link; you send the user to it; they sign in to Outlook or scan a WhatsApp QR code; we tell your server the new account_id.

  1. Mint the link from your server, with notify_url set.
  2. Send the user to url before expires_at (default 30 minutes). The link is bound to the browser that opens it — reopening it elsewhere is 403 link_browser_mismatch.
  3. Read the account id off your notify_url, which we POST server-to-server the moment the account connects. Do not depend on the browser completing its redirect; it may never come back.

success_redirect_url and failure_redirect_url must be absolute http(s) URLs whose host is this deployment’s own origin or on your redirect-domain allowlist (Dashboard → Settings → Redirect domains). Anything else is 400 invalid_url, which is what stops a stolen key from bouncing your users to somebody else’s site.

WhatsApp is a linked device, not the Business API. The user links this service the same way web.whatsapp.com links — the connect page shows them that, and asks them to accept it, before any QR code appears. They can revoke it from the phone at any time (WhatsApp → Settings → Linked devices → Log out), which flips the account to status: "CREDENTIALS" and emits account_status. Relinking needs a fresh hosted-auth link; pairing the same number again keeps the existing account_id, its webhooks and its stored chats.

Webhook delivery

A kind: "webhook" hook receives the JSON above, with these headers:

X-Outlook-Event: chat_received
X-Outlook-Delivery: 1                    # attempt number, 1 for a first delivery
X-Outlook-Signature: sha256=<hex hmac>   # only when the hook has a secret

Verify the signature over the raw request body, constant-time:

mac := hmac.New(sha256.New, []byte(secret))
mac.Write(rawBody)
want := "sha256=" + hex.EncodeToString(mac.Sum(nil))
ok := hmac.Equal([]byte(want), []byte(r.Header.Get("X-Outlook-Signature")))
  • Answer 2xx within 15 s. Anything else — including a 3xx redirect, which is never followed — counts as a failure.
  • Failures retry on a fixed schedule after the immediate first attempt: 30s, 2m, 10m, 30m, 2h, 6h, 12h. After the last one the delivery is marked dead and kept for inspection (DELIVERY_RETENTION_DAYS, default 7).
  • Delivery is at-least-once. Dedupe on the message id; X-Outlook-Delivery tells a redelivery from a first attempt.
  • GET /api/v1/webhooks/{id}/deliveries is the queue: what is waiting, what was abandoned, and why.

Two other kinds post a short human notification instead of JSON, on the same event filter and the same retry schedule: discord (a discord.com/api/webhooks/… incoming-webhook URL) and telegram (a bot_token from @BotFather plus a chat_id). A Telegram target is checked against Telegram once at registration, so a bad token fails on the create call rather than silently at delivery time.

Errors

Every error is the same shape, whatever produced it:

{
  "error": { "code": "missing_account_id", "message": "account_id is required" }
}

Branch on code, never on message — the wording may improve, the code will not change.

Self-hosting

Entropix is one static Go binary with its UI embedded — no build step, no asset pipeline, no sidecar. It stores everything in SQLite by default and speaks Postgres when you point it at one. GET /healthz is the readiness probe.

If you enable WhatsApp, note that the linked-device keys live in this service’s own database unsealed — unlike OAuth refresh tokens, which are AES-256-GCM sealed before they touch disk. Anyone who can read the database file can impersonate a linked device, so run it behind disk-level encryption.
